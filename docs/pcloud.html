1. Konzept & Architektur

Die pCloud-Tools implementieren Content-based Deduplication für Cloud-Backups ähnlich wie rsync --hard-links, aber in der Cloud. Lokale RTB-Snapshots werden in JSON-Manifeste konvertiert und mit SHA256-basierter Deduplizierung zu pCloud hochgeladen.

Kernprinzip: JSON-Manifest-Architektur

Statt jeden Snapshot komplett hochzuladen, werden nur Metadaten + Verweise gespeichert:

Traditionelles Backup pCloud-Tools (Dedupliziert)
3 Snapshots à 90 GB = 270 GB Upload 1× 90 GB Upload + 2× JSON-Manifeste (~20 MB)
Jede Datei mehrfach in Cloud Gleiche Datei (SHA256) nur 1× gespeichert
Kein Index, langsame Restore Fast Restore via Manifest

2.5 Operational Improvements

Paritäts-Cleanup für Manifeste aa1cdcb

Problem: RTB Retention löschte alte Snapshots → Remote-Snapshot gelöscht via retention_sync → Lokales Manifest blieb orphaned in /srv/pcloud-archive/manifests/

Lösung: Automatisches Manifest-Löschen synchron mit Remote-Snapshot-Deletion:

# pcloud_push_json_manifest_to_pcloud.py (retention_sync_1to1)
pc.delete_folder(cfg, path=rmpath, recursive=True)

# Paritäts-Cleanup:
manifest_dir = os.path.join(os.getenv("PCLOUD_ARCHIVE_DIR", "/srv/pcloud-archive"), "manifests")
manifest_file = os.path.join(manifest_dir, f"{snapshot}.json")
if os.path.exists(manifest_file):
    os.remove(manifest_file)
    print(f"[retention] Manifest gelöscht: {snapshot}.json")

Vorteil: 1:1 Parität (snapshot weg = manifest weg), keine Orphans, kein extra Cronjob, Smart-Mode Safety

Intelligent Gap-Backfilling 84d907d

Problem: Alte Logik lud nur latest Snapshot hoch → Bei pCloud-Blockade über mehrere Tage entstehen lokale Snapshots S1-S4, aber nur S4 wird hochgeladen → Nach RTB-Retention fehlen S1-S3 permanent in Cloud!

Lösung: Wrapper iteriert jetzt ALLE lokalen Snapshots, prüft jeden gegen Remote, lädt fehlende chronologisch hoch (alt → neu):

# wrapper_pcloud_sync_1to1.sh (neue Logik)
for s in $(local_snapshot_names); do
  if [[ "$(remote_snapshot_exists "$s")" == "NO" ]]; then
    log "[gap] Snapshot $s fehlt remote – hole nach..."
    build_and_push "$RTB/$s"
  fi
done

# Output bei 4 fehlenden Snapshots:
[check] Prüfe auf fehlende Snapshots...
[gap] Snapshot 2026-04-08-120000 fehlt remote – hole nach... (~20min)
[gap] Snapshot 2026-04-09-120000 fehlt remote – hole nach... (~5min, Stubs!)
[gap] Snapshot 2026-04-10-120000 fehlt remote – hole nach... (~5min, Stubs!)
[gap] Snapshot 2026-04-11-120000 fehlt remote – hole nach... (~5min, Stubs!)

Vorteile:

  • Self-Healing: Gaps füllen sich automatisch beim nächsten erfolgreichen Lauf
  • Lückenlose Historie: Alle RTB-Snapshots auch in Cloud verfügbar
  • Effizient: Smart-Mode Deduplizierung → S2-S4 nur Stubs (KB statt GB), nur ~5min/Snapshot
  • Immun gegen Ausfälle: pCloud 4 Tage offline? Kein Problem, nachziehen kostet ~35min statt 80min
Performance: S1 (erster) ~20min Full-Upload, S2-S4 jeweils ~5min (99.99% dedup). Total ~35min für 4 Snapshots statt 4×20min = 80min ohne Deduplizierung.

3.5 Chunked Upload with Resume (Large File Support)

Status: Production-Ready seit April 2026 7d988a4 10249fc

Problemstellung: Große Dateien (>5 GB) wie VM-Images oder vollständige Backup-Archives brachen bei Netzwerkunterbrechungen von 0 neu an. 98% Upload → Timeout → 100% Neustart ❌

Lösung: Chunked-Upload mit State-Persistenz → Resume bei Unterbrechung ✅

Architektur & Funktionsweise

# Smart Routing (in pcloud_push_json_manifest_to_pcloud.py):
_upload_file_smart():
  file_size = os.path.getsize(local_path)
  if file_size > 5 GB:
      → _upload_file_resumable()   # Chunked mit Resume
  else:
      → pc.upload_file()            # Standard (wie bisher)

Features

  • Threshold-basiert: Nur Files >5 GB nutzen Chunked-Upload (kein Overhead für 99% der Dateien)
  • State-Persistenz: Nach jedem 128 MB Chunk wird State gespeichert (/srv/pcloud-archive/resume/*.state.json)
  • Server-Sync: upload_info() prüft Server-Offset vor Resume (verhindert Duplikate)
  • Retry-Logik: 5 Attempts pro Chunk mit Exponential Backoff (2-16s)
  • SHA256-Verifikation: Nach Upload wird checksumfile() mit lokalem Hash verglichen
  • Automatic Resume: Bei Script-Neustart wird State geladen und bei letztem Offset fortgesetzt
Dateigröße Methode Chunks Upload-Zeit Resume-Fähig
< 5 GB Standard-Upload N/A Normal ❌ (von 0 neu)
6 GB Chunked (48× 128MB) 48 +5% overhead ✅ (bei Abbruch)
20 GB Chunked (160× 128MB) 160 +5% overhead ✅ (bei Abbruch)
50 GB Chunked (400× 128MB) 400 +5% overhead ✅ (bei Abbruch)

4.1 RTB Wrapper Integration

Vollautomatische Backup-Pipeline via rtb_wrapper.sh → wrapper_pcloud_sync_1to1.sh:

#!/bin/bash
# /opt/apps/rtb/rtb_wrapper.sh

# 1. Safety-Gate Check
safety_gate.sh --strict || exit 2  # RED/YELLOW → ABORT!

# 2. Check für Änderungen
if rsync -ni --delete /srv/nas/ /mnt/backup/rtb_nas/latest/ | grep -qE '^[<>ch*]'; then
  # 3. RTB-Backup fahren
  bash rsync_tmbackup.sh /srv/nas /mnt/backup/rtb_nas excludes.txt
  
  # 4. pCloud-Sync triggern (shared lock!)
  BACKUP_PIPELINE_LOCKED=1 bash /opt/apps/pcloud-tools/main/wrapper_pcloud_sync_1to1.sh
else
  log "[skip] Keine Änderungen → kein Backup nötig"
fi

4.2 Wrapper pcloud_sync_1to1.sh

Orchestriert Manifest-Erstellung, Upload, Verification mit Smart-Mode Auto-Detection und Gap-Backfilling:

#!/bin/bash
# wrapper_pcloud_sync_1to1.sh

SNAP=$(readlink -f /mnt/backup/rtb_nas/latest)
SNAPNAME=$(basename "$SNAP")

# 1. Manifest erstellen (Smart-Mode auto-detect!)
MANIFEST_MODE="smart"
last_manifest=$(find /srv/pcloud-archive/manifests -name '*.json' | sort -r | head -n1)

if [[ -n "$last_manifest" ]]; then
  ref_arg="--ref-manifest $last_manifest"
  log "[manifest] Smart-Mode: Nutze Referenz-Manifest $(basename "$last_manifest")"
else
  log "[manifest] Smart-Mode: Kein Referenz-Manifest (Full-Mode für ersten Snapshot)"
fi

python pcloud_json_manifest.py \
  --root "$SNAP" \
  --out /srv/pcloud-temp/pcloud_mani.${SNAPNAME}.$$.json \
  $ref_arg \
  --hash sha256

# 2. Upload (mit Retry + Parallel Folders + Timeouts!)
python pcloud_push_json_manifest_to_pcloud.py \
  --manifest /srv/pcloud-temp/pcloud_mani.${SNAPNAME}.$$.json \
  --dest-root /Backup/rtb_1to1 \
  --snapshot-mode 1to1 \
  --env-file .env

# 3. Verification
python pcloud_quick_delta.py \
  --dest-root /Backup/rtb_1to1 \
  --env-file .env \
  --json-out /srv/pcloud-temp/delta_verify_${SNAPNAME}.json

# 4. Cleanup (explizit, NICHT via trap RETURN!)
rm -f /srv/pcloud-temp/pcloud_mani.${SNAPNAME}.$$.json

6. EntropyWatcher Integration

Die Backup-Pipeline nutzt EntropyWatchers Safety-Gate um Backups während Ransomware/AV-Incidents zu blockieren.

Safety-Gate Status Codes

Exit Code Status STRICT=0 (Lenient) STRICT=1 (Strict)
0 GREEN ✓ Backup runs ✓ Backup runs
1 YELLOW ⚠ Backup runs with warning ❌ Backup blocked
2 RED ❌ Backup blocked ❌ Backup blocked

Safety-Gate Checks

  • Entropy-Anomalien: Verschlüsselte/komprimierte verdächtige Dateien
  • ClamAV Findings: Malware-Signaturen
  • Scan Age: Scans nicht älter als Fenster-Größe (z.B. 75min)
  • Honeyfiles: Zugriffe auf Köder-Dateien (Tier 1 = kritisch!)

Integration in RTB Wrapper

# rtb_wrapper.sh
SAFETY_GATE_STRICT=1  # Empfohlen: auch YELLOW blockiert!

if [[ "$SAFETY_GATE_STRICT" -eq 1 ]]; then
  "$ENTROPYWATCHER_SAFETY_GATE" --strict
else
  "$ENTROPYWATCHER_SAFETY_GATE"
fi
STATUS_CODE=$?

case $STATUS_CODE in
  0) log "[safety] ✓ GREEN - Backup darf starten" ;;
  1)
    if [[ "$SAFETY_GATE_STRICT" -eq 1 ]]; then
      log "[ABORT] ⚠ YELLOW - Backup BLOCKIERT (strict mode aktiv)"
      exit 1
    else
      log "[safety] ⚠ YELLOW - Backup läuft mit Warnung"
    fi
    ;;
  2)
    log "[ABORT] ✗ RED - Backup BLOCKIERT! (Ransomware/Viren-Verdacht)"
    exit 2
    ;;
esac

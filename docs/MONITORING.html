Monitoring & Logs

Diese Seite beschreibt zwei Dinge: die Backup-Pipeline (RTB auf die SSD, dann Upload nach pCloud) und EntropyWatcher (Scans, Safety-Gate). Bei „Backup fehlgeschlagen“ zuerst den Abschnitt Backup-Pipeline — Fehleranalyse — nicht nur das EntropyWatcher-Journal.

Backup-Pipeline — Fehleranalyse

Typische Auslöser: backup-pipeline.service steht auf failed, der Timer (04:00 / 12:00 / 20:00) hat nichts fertig gemacht, oder du willst wissen, ob pCloud noch arbeitet (activating ist oft normal während copyfolder).

Zwei Logdateien (auf pi-nas):

  • /var/log/backup/rtb_wrapper.log — Safety-Gate, RTB-Staging, Start/Ende des pCloud-Wrappers
  • /var/log/backup/pcloud_sync.log — nur der pCloud-Upload (beginnt mit pCloud Sync 1to1 Start)

Schritt 1 — systemd: Ist ein Lauf aktiv oder abgebrochen?

systemctl is-active backup-pipeline.service
systemctl list-timers backup-pipeline.timer --no-pager

journalctl -u backup-pipeline.service --since today --no-pager \
  | grep -E 'Starting|Started|Failed|exit-code|status=|Main process exited'

So liest du das:

  • activating — der Oneshot läuft noch (RTB oder pCloud). Bei pCloud kann das viele Stunden sein.
  • failed + Exit 2 nach wenigen Sekunden — sehr oft Safety-Gate RED (siehe Schritt 2), nicht „pCloud hängt“.
  • active / inactive mit status=0/SUCCESS — letzter Lauf durch.

Schritt 2 — Warum blockiert das Safety-Gate? (RTB-Log)

sudo grep -E 'SafetyGate|ABORT|safety\]|done\]|error\]|pCloud' \
  /var/log/backup/rtb_wrapper.log | tail -80

/opt/apps/entropywatcher/main/safety_gate.sh; echo "exit=$?"

safety_gate.sh: Exit 0 = GREEN, 1 = YELLOW, 2 = RED. Standard backup-pipeline.service: SAFETY_GATE_STRICT=0 — YELLOW blockiert nicht, RED schon.

Im LogWas es bedeutetWas du tun kannst
RED, Honeyfile / Audit Backup wird bewusst nicht gestartet (Exit 2). sudo ausearch -k honeyfile_access --start recent — welcher Prozess? (z. B. nächtlicher clamscan auf eine Köderdatei)
YELLOW, too_fresh_to_trust Entropy-Scan ist jünger als die Abkühlzeit (~10 min). Warten oder erneut prüfen; mit STRICT=0 läuft die Pipeline trotzdem weiter.
[done] RTB erfolgreich dann pCloud-Sync POOL-MODE Staging auf der SSD ist fertig, Upload läuft oder folgt. Schritt 3 — pcloud_sync.log

Diagramme: RED (blockiert) · YELLOW (STRICT vs. Standard)

Schritt 3 — pCloud: hängt copyfolder oder läuft der Upload?

sudo tail -f /var/log/backup/pcloud_sync.log

sudo grep -E 'Struktur geklont|copyfolder: warte|Phase 4|Complete' \
  /var/log/backup/pcloud_sync.log | tail -20

sudo pgrep -af 'wrapper_pcloud|pcloud_push_json_pool' || true

So liest du das:

  • Nach RTB oft Safety-delay, dann Checking for missing snapshots — dazwischen kann es minutenlang still sein (pCloud-API).
  • Phase 1: Klone Basis-Snapshot — serverseitiges copyfolder; Heartbeat etwa alle 15 min (copyfolder: warte), Dauer von ~15 min bis mehrere Stunden ist normal.
  • pCloud Sync 1to1 Complete — Upload für diesen Snapshot fertig.

Schritt 4 — Erneut starten (nur wenn Gate nicht mehr RED)

sudo systemctl start backup-pipeline.service

Ein fehlgeschlagener Oneshot bleibt in failed, bis ein Lauf erfolgreich durch ist — das ist systemd-normal, kein „hängender Zombie“.
